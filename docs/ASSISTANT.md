# Assistant and personalization

## One assistant

Vittaz has one assistant. `packages/core` defines an `AssistantService` port, and `packages/agent` implements it. The Android chat, the CLI and Telegram all call it. Each message carries a `source` (`app`, `cli` or `telegram`) and a conversation identifier. The source says where a message came from. It does not choose a different AI.

The provider boundary lives only inside `packages/agent/src/providers`, as a Vittaz-owned contract over the Anthropic and OpenAI-compatible transports. The core never imports it, and no third-party agent framework is installed, so a provider can be replaced without touching financial logic.

## Fixed workflows and the one open loop

Most features are fixed workflows. The code decides the steps, and a model fills in blanks.

| Feature                    | Who decides the steps                              | Model calls                 |
| -------------------------- | -------------------------------------------------- | --------------------------- |
| Manual entry               | Code                                               | 0                           |
| Notification parsing       | Code (rules), local model only for unknown formats | 0 or 1, local               |
| "Paid 450 to Aman"         | Code                                               | 1, to turn text into fields |
| Improve note               | Code                                               | 1, local                    |
| Daily digest               | Code computes numbers                              | 0 or 1                      |
| Questions about the ledger | The model, within limits                           | A few                       |

Only ledger questions use an open tool-calling loop. It is capped by a step limit, a token budget and a timeout, and it can use read-only tools.

## Tools

Tool names use `snake_case`. The application registers them. The model chooses among the ones it is given.

| Tool                  | Access                          | Purpose                                             |
| --------------------- | ------------------------------- | --------------------------------------------------- |
| `propose_transaction` | creates a pending proposal only | Draft an entry for approval                         |
| `find_person`         | read-only                       | Look up a counterparty                              |
| `query_transactions`  | read-only                       | Filter by date, category, account, person or status |
| `get_balance`         | read-only                       | Balances, receivable and payable                    |
| `get_month_summary`   | read-only                       | Spent, received and totals for a month              |
| `check_unverified`    | read-only                       | Entries waiting for confirmation                    |

Local-model tasks that are not tools: `parse_entry`, `improve_note`.

Never exposed to the assistant: approve, reject, undo, import, backup, restore, settings and credentials.

## Conversation history

History is stored locally and shared across channels. Opening the app shows conversations that began on Telegram. When history is sent to a cloud model, only recent turns go, after the privacy filters in [Privacy](PRIVACY.md).

## Memory

V1 has no automatic long-term memory, no vector database and no background learning. A cache is not memory. A later version may add a small context sheet generated by code from the ledger (categories, frequent merchants, aliases), not learned by a model.

## Personalization

The settings screen calls this Assistant personalization. It has two parts.

**Preferences:** tone, language (English, Hindi or Hinglish) and level of detail. Stored locally and added to the assistant's context.

**Custom rules:** two kinds.

- _Behavior rules_, such as "show amounts in rupees" or "keep summaries short". These guide the model but never override [Agent policy](AGENT_POLICY.md).
- _Message conditions_, such as "only accept messages from my paired chat". These are enforced in code before a message reaches the assistant.

Rules are validated structured settings, not free-form system prompts. A secret phrase in a message is not authentication. Authentication happens before the assistant sees anything.

Every AI proposal already needs approval, so there is no "ask me above a threshold" rule. All proposals ask.

### Implemented local history boundary (S27a)

Core defines ConversationHistoryStore, startConversation and
recordConversationMessage; storage exposes OperationalStore.history on its existing
serialized connection. Each message has source app/cli/telegram and a conversation
ID. Only user/assistant text is accepted; IDs/canonical UTC timestamps come from
the host, not model tools. Sensitive messages drop before persistence. Raw local
names/text are not implicitly uploaded/redacted by this persistence API.

Recent reads default50/max100. Messages are ordered by private SQL append sequence,
not timestamp/random ID, so equal/backward clocks cannot reorder user/assistant
turns. Sequence is neither supplied nor exposed by the port. Conversation overview
uses created_at/id. Appending to a missing conversation, duplicate IDs or closed/reentrant access
fail closed; no SQL/parameter text escapes. No raw connection/write history port
is added to read-only QA tools. Shared AssistantService/channel/privacy-context
integration is still S27d/S28, not proved by persistence tests.

History is currently local plain SQLite, without a new encryption, synchronization,
retention/deletion or backup mechanism. Existing JSON backups remain **ledger-only**
formatv1/payload schemaVersion2, even though DB schema is3: they exclude chats.
Restoring one preserves existing chats; moving only that backup does not transfer
chat history. Do not label it a full application/history backup.

### Implemented preferences (S27b)

OperationalStore.preferences persists strict tone neutral/friendly/formal, language
english/hindi/hinglish and detail concise/balanced/detailed. Defaults are neutral,
English and balanced; no free-form system instructions. Q&A options accept a
validated snapshot and append presentation-only context to the existing safety
policy. Persisted values are tested through real framework/fake HTTP. Automatic
service loading comes in S27d; the model has no settings-writing capability.
Ledger-only backups exclude preferences and preserve them on restore, like chats.

### Implemented structured rules (S27c)

OperationalStore.rules stores exact validated rule arrays. Behavior rules are
amounts_in_rupees and short_summaries; message conditions are allowed_sources
(app/cli/telegram) and paired_telegram_only. No free text, automatic approval or
threshold rules. Unauthenticated origins and unpaired Telegram are always denied,
even with no custom rules. Code checks conditions before redaction/model/tool
execution. Paired Telegram reminder never disables the base pairing requirement.

The host must verify authentication/pairing and supply exact origin metadata; a
phrase or field inside a user/model message is not authentication. Low-level QA
options accept rules plus verified origin for integration; do not expose a client
controlled origin object as an authenticated API. S27d/S28 implement actual host/
channel wiring. Presentation context cannot change code permissions or approvals.
Ledger-only backups exclude rules and preserve local rules on restore.

### Shared service and notification worker (S27d)

SharedAssistantService implements the core AssistantService.handle port. Channels
supply VERIFIED origin separately from the strict body (request_id, conversation_id,
action, text). Explicit actions question/draft_entry/improve_note keep workflows
fixed. Questions use the bounded read-only agent and only six recent privacy-
filtered untrusted turns; drafts use one validated local parse and the existing
propose_transaction validator to create pending only; note improvements are local
suggestions and never applied to a ledger note. No fallback to cloud parsing.

Sensitive or unauthenticated/unpaired inputs have zero storage/model effects.
Stored conditions apply before history creation; accepted user history can remain
after computation fails/cancels. Request IDs prevent duplicate inference. Native
pending writes check cancellation inside the serialized transaction, both before
and after writes (rollback on expiry). SQL/JS cannot be forcibly preempted; trusted
adapters remain responsible for honoring their capabilities/signals.

AssistantNotificationWorker uses existing deterministic allowed-app ingestion
first (zero model calls for known formats), then local parsing only for an unknown
route. Unknown results can create pending only, never automatically commit AI
interpretation. It has no cloud client. Conversational rules gate unknown inference,
not already authorized deterministic ingestion. Android/channel adapters still
need permission/authentication/worker wiring; backend tests are not device proof.

### Telegram backend (S28)

TelegramConnector consumes only verified getUpdates from TelegramHttpApi. Token,
primary_device, paired_chat_id and durable offset come from TelegramSettingsPort,
which the trusted host MUST implement using secure platform settings (not generic
app_settings). No token write API/backup/history/analytics/logging. No actual Android
Keystore or foreground-service implementation is claimed by this backend port.
Host generate_pairing_code MUST be cryptographically random six digits and now
returns trusted integer milliseconds. beginPairing is a local owner API, never an
AI tool. Code is memory-only, five-minute expiry, five failed attempts maximum,
consumed once; existing paired chat cannot be replaced by a message. Private chats
only; everyone else gets no response and no ledger/history/model processing.
Sensitive messages likewise drop before AssistantService. Cursor-only bookkeeping
is maintained even for ignored updates (no content retention). Accepted paired
messages use source telegram, trusted origin and shared conversation main; stable
bot/update request IDs prevent duplicate inference. Questions only, not approvals
or admin commands. Safe replies only to paired chat, plain text/truncated4096.

Primary-device false disables transport. One in-flight poll/digest per instance;
409 latches until operator resolves the other poller/webhook and recreates instance.
429 returns retry delay and blocks both poll/digest until elapsed. Caller owns
poll scheduling/lifecycle (no implicit background loop); must inspect status and
not busy-spin on errors. Offset durable via host secure port. Network delivery is
not exactly-once: a send failure after accepted history can lose a reply; replay
cannot duplicate inference/proposals. Android service/restart delivery remains
phase I testing. No Telegram live call was made. Digest input is validated integer
unverified_count/daily_allowance_paise, formatted deterministically with BigInt
(no AI, names or notes); caller computes counts/allowance with core query/calculator.
